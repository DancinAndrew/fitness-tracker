# Design draft

狀態：未實作；已確認 Remote 主入口及簡單前端方向，D1 共用帳本為新版架構提案，沒有啟用新服務。見 [ADR 0002](../../../docs/adr/0002-shared-cloud-ledger-and-sites.md)。

## Responsibility boundary

```text
iPhone：照片／短句／系統聽寫文字
  → Codex Remote：辨識、提出候選值、解釋不確定性
  → Sites 受保護工具：驗證、日期／單位／份量運算、確認與版本控制
  → D1 雲端正式帳本 ←→ Sites 前端：摘要／查閱／補充／趨勢
  → 確定性摘要 → Codex：說明、最少量建議

Mac 私人目錄：原始照片、未送出草稿與備份（不作另一份正式帳本）
```

D1 是 Sites 支援的持久雲端資料庫。Sites 後端採相容的 TypeScript，運算與驗證集中為同一套服務，供前端 API 與 MCP 使用；MCP 是供 Codex 呼叫受限操作的工具介面。Mac 不另實作一套 Python 營養計算，也不開外網連入 Mac 的埠。Codex 是主要輸入介面及分析者，網站不呼叫新的模型 API，不公開任意 Codex／shell／SQL 執行能力。

## Canonical data

唯一正式帳本為 D1，原始附件留 Mac 的 `.private/`。本機待送出資料只是草稿，不能當雲端已保存或被納入已保存累計。網站先不看原圖，R2 維持未啟用。雲端僅保存必要運動、飲食、量測與計畫資料；私人 seed 需明確選欄匯入，排除敏感背景。`.private/` 被 Git 忽略不等於加密；備份位置與復原流程需驗證。

邏輯實體：profile、plan_version、workout、exercise_set、cardio_log、dance_log、meal、meal_item、asset、analysis_revision、measurement、recovery、recommendation、plan_change。實際資料表由實作時的小型 migration 定義，不能將附件 JSON 整體當 schema。

每筆來源值保留 source_type、原始描述／資產引用、日期／單位與確認狀態。自述、測量、包裝標示、視覺估計、推導、目標及建議分開；攝取狀態與營養可信度是不同欄位。估算已吃的餐可入帳；營養未知為 null，不算零。

所有時間保留上傳時間與實際事件時間。依 Asia/Taipei 歸日，預填今天標為待確認。資料庫以單一有效版本供累計，保留修正歷史及支持摘要的紀錄集合。

## Controlled writes

先規劃操作合約，再實作共用服務、前端 API 與 MCP 工具：建立／修正餐點草稿、確認攝取、記錄訓練／量測、查詢今日計畫與累計、產生回顧、保存一般備註、提出／確認計畫調整、匯出／刪除。Sites 原生 plugin 連線先測唯讀及身分再測寫入；不預設安裝或登入已完成。

後端驗證完整 payload 及使用者權限；以固定精度整數／有理份數與明確四捨五入規則處理份量及營養，避免浮點累加漂移。使用 D1 支援的原子操作與唯一 request_id，避免 Remote 重試寫入兩次。修正要指定 record_id 與 expected_revision；版本不符時重新讀取，不能默默覆蓋另一個入口的更新。資料庫操作採參數化 SQL，schema migration 與真實紀錄寫入分開。

照片以雜湊提示可能重複，不直接禁止同照片代表不同次進食。多張餐照、標示、餐後照應附屬同一餐，不生成多餐。保存成功後重新查讀，才回覆「已記錄」。模型不能直接輸出一個當日合計當資料庫真值。

相同 exercise_id、負荷模式與重量才可比較進階；驗證全部工作組、雙側、次數上限、餘力、動作控制、恢復與連續兩次的規則。證據缺少或有異常症狀時不觸發加重建議；建議始終等待使用者確認。

## Image handling

首個技術探勘要驗證 Remote 附件是否能在本機取得原始位元組。若只能看見影像但無可保存附件，不把聊天顯示當成持久保存；需提供支援的檔案匯入路徑並重新驗證。不得爬取帳號私有端點或擅自改用公開圖床。

讀取食物、營養標示、跑步機面板與體重計；保留原圖及擷取欄位的來源。模糊數字、未見單位、面板輪播不完整時為待確認。當下速度／坡度不得當作全程平均；機器估算消耗單獨保存，不抵銷飲食攝取。

手機日期／定位中不必要的 EXIF（照片附帶的位置等中繼資訊）應在長期保存前移除；不能假設模型能看見或正確使用 EXIF。影像尺寸／格式支援及轉換於真機探勘確認，避免承諾未驗證的 HEIC 行為。

模型／網路失敗保留草稿與已保存附件，可稍後重試；不出現假成功或零營養。Mac 離線時 Remote 無法即時分析；網站仍可查看雲端已保存資料並作簡單補充。Mac 恢復連線後可指定實際日期補傳；不假設已有可靠背景佇列。若網站服務暫時不可用，畫面保留輸入並明示未保存。

## Frontend and data refresh

一個手機可用的 dashboard，提供今日、紀錄、趨勢三個區塊。今日顯示課表與狀態、已回報營養範圍、餐數及待確認；紀錄按日期查閱、修正份量、補量測或一般備註；趨勢顯示有效體重平均、腰圍、訓練表現及已回報飲食。

開頁／回到頁面／手動更新時重新查詢，網站保存後立即重抓；顯示最近取得資料時間及保存狀態。Mac 保存紀錄不用重建或部署網站。第一版沒有跨裝置即時推播、完整離線編輯或雙向資料庫同步。

一般文字備註不自動建立營養／訓練紀錄，不擅自修改課表。下次 Codex 查詢取得備註與有效紀錄，而非靠聊天記憶同步；新增備註不會自動喚醒 agent。網站不顯示 Mac 檔案路徑，沒有照片雲端儲存時不製造無效縮圖。

## Nutrition and recommendations

逐食物計算每份／每百克密度、整包份數、實際比例與營養範圍。標示熱量不被三大營養素近似換算覆蓋。範圍合計只是帳本範圍，並非統計信賴區間。

摘要只計 confirmed_consumed 的有效版本，明列回報幾餐與未知營養。未回報不等於未進食。補食物建議依已知缺口與資料完整度，最多一至兩個品類及標示條件；若足夠則不用補。商品精確資料需來源與核對日；不杜撰價格或庫存。

## Trend and plan history

體重用固定七日視窗內有效晨重，顯示樣本數，至少三筆才給平均趨勢；不能把最近三筆不論日期當一週。兩週回顧須檢查兩個視窗、腰圍、訓練表現、恢復及回報完整度。缺證據先補資料。

四週之後仍保存並查詢歷史。新計畫由確認事件建立新版本與生效日，不改寫舊課表或執行紀錄。見面日前減量規則只在目標日確認後才可規劃；所有強度／熱量調整仍需確認。

## Verification strategy

以選定 Sites starter 的測試工具為準，驗證 TypeScript 確定性核心及 D1 相容本機／隔離資料庫整合；採用新套件前說明必要性。合成 fixture 不能出現在真實帳本。需另驗 Remote 與前端同筆紀錄讀寫、權限、revision 衝突、重試以及斷線狀態；雲端存取需要真實部署後驗證，不能以 mock 宣稱串接成功。

T22–T24 等語言／安全案例需「結構化事件規則測試＋實際對話行為檢查」，不能只測關鍵字即聲稱醫療安全保證。T26 需模擬分析失敗、儲存失敗、網路重試；真機測試另記裝置、日期、附件保存及新對話讀回結果。
