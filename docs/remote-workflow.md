# 每天用照片與自然語言紀錄

## 入口與保存位置

在 iPhone 的 Codex Remote 開啟這個 Mac 專案，傳照片並附一句情境。例：「昨天晚餐，飯剩四分之一，肉菜吃完」或「今天跑步機，這是結束畫面」。不用先把數字整理成表格。Mac 必須在線才能讓 Codex 分析；已存資料可直接在 Site 查閱及手動補充。

首次使用要安裝／連接本 Site 提供的私人 plugin。連接後先用 `health_get_settings` 做只讀驗證，再進行保存。沒有這個工具或連接失敗時，保存本機待處理稿並明說「尚未保存到網站」，不透過偽造身分、service token 或本機 MCP 設定繞過登入。

原照片在 Mac `.private/assets/`；正式結構化紀錄在 Site D1；網站只讀後者。程式碼和去識別化規格可以進 Git。提供者對話／附件、Mac 照片、雲端紀錄、匯出備份是不同的刪除範圍。

## Codex 執行順序

1. 收到可讀附件後，用 `python3 scripts/private_assets.py ingest <absolute-photo-path> ...` 持久保存；回傳 opaque asset_refs。附件不可讀時明說，絕不聲稱已保存原檔。HEIC／模糊照不能讀到的值保持未知。
2. 查當地事件日期。今天／昨天依 Asia/Taipei 解讀；只憑上傳時間不能推定跨午夜餐點日期。上下文足夠就直接確認，否則只問會改變累計的 1–2 個問題。一般餐照先草稿；「吃完了」是實際攝取確認，不必重問。
3. 由 Codex 判讀，依 `health_create_record` 的 schema 產生結構化資料。各食物分開、標示每份／每100g分母與份數，估計給範圍，油量未知不可補零。`consumed_fraction` 只影響該食物。標示優先於資料庫／目測；不以4/4/9覆寫包裝熱量。
4. 跑步機保留時間、距離、km/mi、速度範圍、坡度是全程還是瞬間。體重照不能證明晨重。啞鈴紀錄分每手／總重／單側、暖身／工作組、左右下數、保留次數RIR、品質與疼痛／恢復；只在必要時追問。
5. 在 `.private/pending/` 寫入完整 command，生成一次 request_id。用 Site 工具保存。失敗／收據遺失保留原 command 與同一 request_id 重試；409 先讀最新版，不能另建一餐來繞過。不可用的模型分析保持 pending/failed。
6. 成功才報「已保存」、record_id、日期與版本，並用 `health_get_record`／`health_dashboard` 讀回。網站刷新即見，不用部署。更正時先讀原紀錄，再以 same id + expected_revision 更新。
7. 回覆簡短摘要：本餐估計／缺漏、目前已回報攝取範圍、1–2 個補足方式或「不用補」。商品沒有可查證標示時只推薦品類／份量；價格與庫存未知。建議絕不自動記成吃過。

## 教練與回顧邊界

依後端今日課表、兩次訓練條件及七日晨重窗口給建議；不憑單日體重或漏報宣告平台期。不以見面期限自動加強度／減熱量。設定的生效日期、目標與已完成紀錄分開。加重建議首版只顯示，沒有暗中保存新的重量處方。

嚴重胸痛或異常呼吸等回報應停止當下訓練建議，依情境建議及時醫療協助；以 `safety_hold:true` 阻止進階。單餐照不能診斷營養缺乏、荷爾蒙或疾病。敏感健康困擾不寫入普通備註、不診斷或提出治療／未確認補品。

## 匯出、備份與刪除

`health_export` 只匯出雲端資料及設定歷史，原照片另外備份。使用者要求備份時，把匯出存入 `.private/exports/`，再用 `private_assets.py backup <path>` 建本機備份。`restore` 先回復到隔離新目錄並驗證雜湊，不直接覆寫現有紀錄。雲端還原須經正常工具逐筆驗證、處理版本，不把匯出 JSON 當成已還原。

雲端 delete 擦除該紀錄及內容版本；為防重試復活會保留不含健康內容的失效收據。刪除本機照片前須查其 asset_ref 是否仍被其他紀錄使用，並得到明確照片刪除要求。Mac 離線時列出尚待刪除的檔案範圍。備份／提供者對話不會跟著單筆刪除自動清掉。
